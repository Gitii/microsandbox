Both of you are circling the right issue, but the debate is anchored on the wrong word. "Corruption" is mostly a red herring; the real questions are crash consistency, rollback semantics, and fencing. Here's how I'd break it down.

**Where appcypher's corruption fear is overstated.** A point-in-time snapshot of a running VM's disk is exactly equivalent to the state you'd have after a power cut at that instant. That's a well-understood domain — it's called a crash-consistent snapshot, and it's what EBS and GCP PD snapshots do to running disks every day, on by default, with no user opt-in. Journaling filesystems (ext4 in the guest) recover cleanly from it; databases with WALs recover from it; that's what those mechanisms exist for. "A program was mid-way through non-atomic writes" describes every power loss ever, and workloads already have to survive that because your nodes can already die today. Restoring from a crash-consistent snapshot doesn't introduce a failure mode the workload wasn't already exposed to.

**The one place his fear becomes real** is if the snapshot isn't actually point-in-time — i.e., you copy the disk file over a multi-second window while the guest keeps writing. A "fuzzy" snapshot like that is genuinely worse than a power cut and can produce states no crashed filesystem would ever be in. So the engineering requirement is: the checkpoint must be an atomic block-level freeze (qcow2 external snapshot / CoW / device-mapper), never a live file copy. If you build that, the corruption argument mostly dissolves.

**Where appcypher has a legitimate point he's not quite articulating.** The novel risk versus a plain crash-reboot isn't torn writes — it's _rollback of acknowledged state_. A sandbox that called external APIs, sent webhooks, or acked work in its final 60 seconds, then resumes from a snapshot before those actions, may redo them. Duplicate emails, replayed jobs, an agent re-executing a step. A pure crash never un-acknowledges anything; a restore-from-stale-snapshot does. That's a real semantic difference and it's the honest version of his objection.

**Where Toks is clearly right.** The comparison isn't "1-minute-old state vs. perfect state" — the node is dead. It's "1-minute-old state vs. hours-old state or nothing," and the former strictly dominates. And the industry precedent actually cuts Toks's way, not appcypher's: when a GCP host fails, your VM auto-restarts on another host with its disk, crash-consistent, automatically — nobody is asked to opt in, and those VMs run arbitrary customer code. The only difference in your architecture is that local NVMe forces the restored disk to be up to a minute stale instead of zero. That staleness is an RPO number to communicate, not a reason to make thousands of customers hand-resume their sandboxes. "Recovery point objective: ≤60s" on the incident page is a normal, defensible thing for a platform to say.

**The synthesis I'd argue for:**

1. **Auto-recover by default, with an opt-out policy** (`on_node_failure: restore | fail-stop`), not opt-in. Opt-in means in practice nobody sets it and every node failure is a mass outage — the thing keeping Toks up at night stays unfixed. Fail-stop exists for the rare workload that genuinely can't tolerate rollback (external-state coordination, strict exactly-once semantics).
2. **Make restores detectable.** Bump a boot/generation ID visible inside the guest and emit a webhook/event on restore, so workloads that care can reconcile ("I was restored from T-47s, re-check my outbox"). This converts the silent-rollback hazard into a handleable signal and answers most of appcypher's objection.
3. **Keep the snapshot history and manual rollback UI** Toks described anyway — it's the escape hatch if a specific restore does land badly, and it makes the auto-restore decision reversible rather than final.

**Two things neither of you raised that matter more than the corruption debate:**

- **Fencing / split-brain.** The dangerous case isn't a stale snapshot — it's a node that's _partitioned, not dead_. Nomad declares it lost, you restore the sandbox elsewhere, then the old node comes back with the original still running: two live copies, divergent disks, duplicate traffic. Your `KillMode=process` re-adoption design makes this scenario more plausible, not less. You need a fencing step (confirm the node is truly gone, or ensure the old instance is killed/its relay unroutable) before any restore fires. Get this wrong and you'll cause worse incidents than the ones you're preventing.
- **Cost of the cadence.** 1-minute snapshots across the fleet only work with incremental dirty-block tracking (qcow2 bitmaps or similar) — full-disk exports per minute won't survive contact with your bandwidth or the disk-space issues you've already hit with snapshot blobs. The cadence can also be tiered by plan rather than global.

One more honest caveat for Toks's "servers serving realtime traffic" framing: this is a reboot from disk, not a live resume. In-RAM state (the agent conversation appcypher mentioned) is lost either way unless it was flushed to disk — snapshots don't save it, and its loss isn't an argument against them. What auto-restore buys you is that the _durable_ state and the sandbox's existence survive, which is exactly the part users can't reasonably rebuild themselves at scale.

So: appcypher wins the narrow point that unannounced state rollback has real semantics and deserves an escape hatch. Toks wins the design: crash-consistent auto-restore as the default is what every serious platform does for host failure, and the 60-second RPO is a communicable trade-off, not corruption. The genuinely hard engineering is atomic snapshots and fencing — I'd spend the design effort there rather than on the opt-in/opt-out debate.
